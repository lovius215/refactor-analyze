# 功能與 API 分類編號清單及複雜度規則（Index & Complexity Rule）

## 1. `project/index.md` 內容與結構規範

`project/index.md` 是全系統功能與 API 的追蹤總表，遵循以下硬性規定：

1. **分類分組排序（同分類放一起，無法歸類放「其他」）**：
   - 必須依據業務模組或領域分類（例如：`會員與權限`、`訂單管理`、`帳務結算`、`報表與批次`）將同類別的功能或 API 放在同一個分類區塊下。
   - **無法明確歸類的功能、API 或工具程式，一律統一放在最後的「其他」分類**。
2. **唯一編號（ID）**：
   - 每一列必須賦予三位數唯一編號（如 `001`、`002`、`003`...），供後續執行 `analyze <編號>`、`reanalyze <編號>`、`commit <編號>` 直接指定。
   - 產出對應業務邏輯資料夾時，資料夾名稱直接使用該**編號**命名（如 `project/001/`、`project/002/`）。
3. **清單欄位限制（保持精簡、極低 Token）**：
   - 清單表格只記錄 5 個核心欄位：
     1. **編號**（如 `001`）
     2. **功能或 API**（功能名稱、API HTTP Method + Path、或批次排程名稱）
     3. **程式的位置**（程式進入點檔案路徑與 Class#Method，如 `src/controller/OrderController.java#create`）
     4. **複雜度**（`高` / `中` / `低`）
     5. **目前的狀態**（`待分析` / `分析中` / `待確認` / `已完成` / `疑似廢棄` / `略過`）

## 2. 複雜度（Complexity）評估標準

複雜度同時記錄於 `project/index.md` 與各編號資料夾的 `project/<編號>/analysis.md`：

- **第一階段（CLI 0-Token 靜態估算）**：
  - 由 CLI 根據進入點與關聯檔案的程式碼行數（LOC）、條件分支數（`if`/`else`/`switch`/`for`/`while`/`catch` 圈複雜度）與依賴注入數量，0-Token 自動計算初步等級。
- **第二階段（`analyze <編號>` 深入校正）**：
  - 綜合以下指標給出最終複雜度（`高` / `中` / `低`）並於 `analysis.md` 寫明原因：
    - **低（Low）**：單純 CRUD 或頁面展示，分支條件少（$\le 5$）、涉及資料表 $\le 2$ 張、無複雜外部系統呼叫。
    - **中（Medium）**：包含多步驟業務驗證或狀態判斷（分支數 $6 \sim 15$）、跨 $3 \sim 4$ 張資料表讀寫或含單一外部服務串接。
    - **高（High）**：複雜計價/結算/狀態機邏輯（分支數 $> 15$）、深層迴圈或動態 SQL、跨 5 張以上資料表交易、多系統非同步串接或含大量歷史技術債。
